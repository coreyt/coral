The flow ends with the Client App holding a protected resource, the last of eighteen messages, handed to it by the Resource Server. The Resource Server only releases that resource after validating the access token with the Authorization Server and getting back "token valid" — a check triggered by the Client App's own "request resource with token" call. That access token, in turn, was granted earlier when the Client App exchanged an authorization code for it: the Authorization Server validated the code against the Token Store (getting "code valid" back) before replying with the access token. The authorization code itself came from an earlier exchange, where the Authorization Server stored the code in the Token Store and handed a copy to the Client App. That code only existed because the Authorization Server had gathered consent — asking the Consent Service for it, with the User approving scopes directly and the Consent Service reporting consent granted — and had already confirmed the User's identity: the Authorization Server redirected to the Identity Provider for authentication, the User submitted credentials directly to the Identity Provider, and the Identity Provider replied to the Authorization Server that the identity was confirmed. The whole chain began with the User clicking login in the Client App, which sent the initial authorization request to the Authorization Server.
